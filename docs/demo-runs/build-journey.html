How to read this document

Every purple-bordered box below is Aman's own words, quoted directly from the session transcript — typos and all, because that is genuinely how the instructions arrived. Green boxes are what happened as a direct result. Red boxes are something that broke or got caught along the way. Amber boxes are the transferable lesson — the thing worth remembering past this one project.

The point of showing it this way, rather than a cleaned-up summary, is that the real skill on display in this project was never "write a spec" or "call an API." It was a repeating loop: state the goal, let the system work, look at the real output, catch what's wrong, fix the cause not the symptom, and write down why. That loop is visible in almost every section below.

Phase 1 · 19-09-2026, morning

The problem statement, and a hard rule about brainstorming first

The project started from a workshop problem statement, pasted in full. It described a 5-agent system (Orchestrator, Destination Research, Logistics, Budget, Review) for a hypothetical "Plan a 5-day trip to Japan" request. Nothing was built yet.

Aman, opening message 19-09-2026 08:45
I'm sharing the problem statement. Based on this problem statement, we need to create a product. Let's brainstorm first before doing an implementation plan, and let's brainstorm how we can do this technically. What is possible? Feel free to ask questions if you have any doubt before creating any documentation. user askuserquestion tool to ask doubts until we are on the same pge..

That second line is the instruction that shaped the entire project's working style: use the structured question tool, not assumptions, and don't stop until aligned. Claude Code's brainstorming process (a built-in skill called superpowers:brainstorming) is built exactly for this — it hard-blocks writing any spec or code until the human has approved a design in chat.

The brainstorm covered runtime choice (Claude Code native agents vs. hand-rolled orchestration), how agents should get facts, hosting, and the review pattern. Two follow-ups reshaped the plan mid-brainstorm:

Aman 19-09-2026 08:55
We also want to build front end for this... also rather than looking and checking for web search, are there any APIs available that we can use to do it?
What happened
The plan pivoted from "agents use web search for facts" to "agents call named MCP tools backed by real APIs": Google Places Text Search, Google Routes, Frankfurter (currency), Open-Meteo (weather). This is a fundamentally different architecture — named tools with typed JSON responses are deterministic and can be unit-tested; web search results cannot. A Next.js front end with a live agent timeline was added to the scope in the same message.
Pattern worth stealing
A one-line redirect from the human, asked early, changed the entire data-fetching architecture before a single line of code existed. This is the value of the brainstorming gate: the question "are there real APIs?" is far cheaper to answer before Task 1 than after Task 9.

Phase 2 · 19-09-2026, morning

Spec, then a plan, then the discipline files

Once the design was agreed in chat, Claude Code wrote it to a spec document (docs/superpowers/specs/19-09-2026-travel-planner-multi-agent-design.md), reviewed section by section.

Aman 19-09-2026 09:13
spec looks fine, go ahead with the implementation plan and create implementation-plan.md file

Before any implementation started, three process files got set up — and this is worth dwelling on, because it is the single biggest reason the project stayed coherent across two days and dozens of subagent dispatches.

Aman 19-09-2026 09:30
with the development of this, which is sub-agent-driven development, let's create decisions.md separately. Package creation and decision aggregation development are done. Whenever we make any changes apart from the spec, we need to modify the spec file. We also need to have a changelog.md file under the spec folder itself so that we know when the changes have happened and why the changes have happened, and for what reasons.
Aman 19-09-2026 09:38
create feedback.md file whenever I correct you if you make any mistakes, all of those points need to be added as part of the feedback.md so that, in the future, we will not make those mistakes again. This is something you need to make sure of: whenever I correct you, it needs to be added. Whenever any development or anything that we do, this point should be taken care of.
Pattern worth stealing
Three files, three jobs, never merged: decisions.md records every choice a reasonable engineer could have made differently, with the reasoning. changelog.md records every place the shipped code drifted from the approved spec, and why. feedback.md records every correction Aman gave, as a reusable class with a check that prevents it recurring. By the end of the project decisions.md had reached D-036. A future session (or a fresh subagent with zero memory of this conversation) can read these three files and understand exactly what happened and why, without ever reading the chat transcript.

Phase 3 · 19-09-2026, mid-morning

16 tasks, one subagent per task, and a reviewer that actually finds things

Aman 19-09-2026 09:36
go ahead, start with subagent-driven execution from task 1

This invoked a specific Claude Code pattern (superpowers:subagent-driven-development): for each task in the plan, dispatch a fresh implementer subagent with only that task's brief (never the whole plan, never the conversation history), let it write code test-first, then dispatch a separate, independent reviewer subagent that sees only the diff and the brief — never the implementer's reasoning. If the reviewer finds something, the implementer fixes it, and the reviewer checks again. This repeated for all 16 tasks.

The controlling instructions from Aman during this phase were short and mostly sequencing:

"continue with task 3" "can u check it again" "MAKE SURE TO USE /frontend-design:frontend-design skill to build the UI" "continue with task 7 once task 6 is done" "continue with task 10 once task 9 is done"

The actual engineering rigor came from the review loop itself, running without needing Aman to inspect every diff. Three real examples from the transcript:

Caught by the independent reviewer, Task 2
The implementer's own report said tests ran on CPython 3.14.3, not the 3.12 the spec named as a floor (requires-python = ">=3.12"). The reviewer flagged this as unmet even though the tests were green — "the reported GREEN evidence verified behavior on 3.14.3, not the Python version the spec names." Fixed by adding a .python-version file pinning 3.12, re-tested, re-reviewed, confirmed.
Caught by the independent reviewer, Task 3
A commit trailer used Claude Haiku 4.5 where the spec's global constraint named Claude Opus 5 (1M context). Small, but the reviewer called it out as "an explicit binding constraint... not a stylistic choice the implementer gets to override unilaterally."
Caught by the independent reviewer, Tasks 4 and 5 (the same class of bug, twice)
A test asserting "no HTTP call was made on a bad date" had no mock active and no assertion that would actually catch a real network call — it only proved an error was returned, not that the code took the right path to get there. The reviewer named this precisely: "the test would pass identically whether or not a real network call were attempted." Fixed by monkeypatching the HTTP function to raise if it were ever called at all, turning the test into something that would genuinely fail if the guard clause moved.
Pattern worth stealing
A green test suite is not evidence of a correct guarantee — it's only evidence the assertions written happened to pass. The reviewer's real job across all three catches above was asking "what would make this test pass even if the property it claims to prove were false?" That question is answerable by a reviewer with zero context, precisely because it never sees the implementer's intent, only the artifact.

Phase 4 · 19-09-2026, mid-morning

Gemini, Vertex, and why the answer stayed "no"

Partway through, Aman asked a sequence of questions that are worth showing in full because the reasoning matters more than the answer:

Aman, four messages across 15 minutes
rather than using anthropic api key, can we use gemini api key? any resotriction ? give me the handover plan if I want to move to vertex from this... create a md file for this what are the changes required and whether I can do this in claude code or not. but we are running this product on the local server,I will not push this to any cloud...then whether I can use gemini api or not..we will be creating the UI for this...and running the local server...on my system that is part of task 12 onwards..so whether it weil cause any issue if I use gemini api or not?? it will be open URL,. no login we need for this product. but why cant we create the local server so there is no depednency on claude code
What happened
The answer stayed no, and the reasoning was written down rather than just stated: the Agent SDK that powers this whole system runs Claude Code, which only ever calls Claude models — via Claude's own platform, Bedrock, Google Cloud's Agent Platform, or Foundry. A Gemini key cannot substitute, local server or not, because the constraint is the runtime, not the hosting location. Rather than leave it there, a full handover document (docs/standalone-server-handover.md) was written covering exactly what a Phase 2 rebuild on a provider-agnostic server would need — roughly 70% of the existing code (tools, contracts, prompts, fixtures, UI) would carry over. v1 stayed on Claude Code; the standalone path was documented, not built, and explicitly deferred.
Pattern worth stealing
"Why not X" deserves a real, sourced answer even when the answer is no — and when the underlying tension is real (wanting model flexibility later), write the escape hatch down instead of debating it in chat. The handover doc meant this question never had to be re-litigated.

Phase 5 · 19-09-2026 evening – 20-09-2026 morning

Shipping v1, hitting the usage limit, and picking back up

Build continued through the web app tasks (the Next.js UI, the live agent timeline, the SSE streaming route), a committed sample run (trips/sample-japan/), and a handover check. One session interruption is worth showing because of how cleanly it recovered:

System message, after a usage limit reset 19-09-2026 13:21
Your claude.ai usage limit has reset. Continue the task you were working on when the limit was reached; do not repeat work that is already complete.

Because progress lived in decisions.md, the plan file's checked-off tasks, and git commits — not just in conversation memory — picking back up cost nothing. The session also ran /compact twice across the two days (Claude Code's built-in context-summarization), and both times the resulting summary was detailed enough that work continued without re-explaining anything.

The first version shipped to GitHub as a public repo on branch build, with a request to also produce a standalone HTML "run log" of a real request for the workshop cohort to study without needing to run anything themselves — a preference that shaped every later "make a document" request in this project:

Aman 20-09-2026 05:55
Don't create an interactive walkthrough, but create an independent HTML file and save it in this particular repository only so that it can be committed, and give it to the learners.
Pattern worth stealing
A plain, self-contained, committed HTML file beats a hosted interactive artifact for handing something to a workshop cohort — no external dependency, works offline, lives in the repo history, reviewable in a PR. This exact page is built to that same instruction.

Phase 6 · 20-09-2026, early morning

A screenshot breaks the "it's done" story

Once the app was running, Aman used it for real — and immediately found the gap that no amount of code review had caught: the system worked, but only for Japan.

Aman, with a screenshot of the logistics agent card 20-09-2026 06:02
why its checking Japan only... as a user, I can give different destinations and different parameters, so the agents in this particular program should not be specific to any city, any destination, or any parameter. It must be dynamic, and I can give it, and it should be able to handle it. do the check, if anything static., Then make it dynamic... /goal check if anything static ... destinations or any static parameters available as part of the agents and any tools, calls, or MCP servers that need to be made dynamic. A user can give any parameters for the itinerary plan that need to be handled. 1. Once you find out the issues, fix it. 2. Review the issues. 3. Review the fix. 4. With the sub-agent, verify with the QA agent. 5. Until and unless there are no issues identified that are blockers and critical, do the fixes. 6. Once the issues are finalized, stop it and give me the final result.

That six-step instruction became the template for every non-trivial fix for the rest of the project: audit, fix, review, review the fix, independent QA, repeat until nothing blocking remains, then stop and report.

What the audit found
get_rail_route genuinely only ever checked Japan — but the deeper cause was more interesting than "someone forgot a city": Google Routes' TRANSIT mode had been probed live weeks earlier and found to return an empty result for every request inside Japan specifically (verified: identical request to London worked). The fix at the time was a seeded lookup table for Japan rail fares. But nobody had ever added the fallback for everywhere else — so the tool silently reported "could not verify" for every non-Japan route, even though the live TRANSIT API worked fine outside Japan the whole time. Two independent QA passes then found two more real gaps: the web UI hardcoded the literal string "JPY" in the currency display regardless of destination, and the review agent's "matches likes" rule only recognized "temple" as a kind, biasing every non-Japan trip's evaluation.
Pattern worth stealing
The bug was never really "Japan-only." It was "the fallback path for every other case was never written," which is a much more common and much less visible failure — code that works perfectly for the one example everyone tested against, and silently degrades for everything else. The fix was verified live against a second real destination (Paris, Lyon) before it was trusted, not just unit-tested against a mock.

Root cause, not just the symptom
The visible bug was one broken table. The actual cause — missing the GFM header-separator row (|---|---|---|) required immediately after a markdown table's header row — was traced through three layers: the output file, the agent's own template, and the shared skill template all four agents draw from. It was fixed at the template layer, in all four agent files at once, not patched in the one visible file.
Aman 20-09-2026 06:42
you are mentioning any places. For example, in this file, you are mentioning the Eiffel Tower and other places [...] All of this must have a hyperlink so that the user can check and see these places.
What happened
The Google Places API call had been returning a real Maps link (maps_url) for every place all along — it was simply never surfaced in any agent's markdown output. The fix generalized the hyperlink from "hotels only" (the literal ask) to every venue named anywhere in an itinerary, updating the schema, the destination-research agent, the synthesis mapping rules, and the web UI together, then applying it retroactively to the already-committed sample-Japan reference file, since that's what workshop learners actually open.

Phase 8 · 20-09-2026, later morning

A second feature: revising a trip after the fact

Once v1 was solid, Aman raised a genuinely new capability — and immediately set a hard rule about how to approach it.

Aman 20-09-2026 09:12
One major chaneg we want to do as following.. If a user had the plan ready but there was a change in the dates, then this entire project should accept the change in dates and should adjust the plan accordingly. Maybe even in the middle of the trip, if a user wanted to end the trip early or extend the trip, there should be one agent which tackles such user queries and adjusts the travel plan accordingly. As of now, we are just doing the brainstorming related to the change that I am asking you to do. Ask me as many questions as possible until and unless we are not on the same page. Once we agree, then only will we start the building part.

What followed was a genuine back-and-forth — multiple rounds of structured questions (using the same AskUserQuestion tool from Phase 1) covering: does a revision apply before departure only, or mid-trip too; how does the system know what day the traveler is on; what change types are in scope this round; and, deliberately left open for Claude Code to research and recommend rather than ask about: how should a revised trip be versioned on disk. That last one was answered by checking what TripIt and Wanderlog actually do (edit in place, one shareable link, never fork per edit) and noting this repo already follows the identical pattern for its own specs.

Brainstorm, four rounds of AskUserQuestion
Scope: date shift, duration change, mid-trip cutoff. Deferred: budget/likes changes (a different problem). Versioning: overwrite in place, append-only log — researched, not guessed.
Spec amendment, same file
"But do we write in the same spec... or create a new spec itself?" — answered by precedent already set in this exact repo: one living design doc per system, amendments appended, never forked into spec-v2.md.
Implementation plan, 11 tasks
A new classifier agent (trip-revision, read-only, no travel tools — decides what changed, never edits anything itself), a new /revise-trip skill that reuses the existing three worker agents rather than duplicating their logic, a new JSON contract, fixture-based tests, and both a terminal and web entry point.
Built task by task, same discipline as Phase 3
Each task's own verification command run and confirmed before moving to the next — schema validation, structural eval, pytest, tsc, vitest, and a real headless run of the new eval script against three fixtures.
Aman, approving the plan 20-09-2026 09:48
lets go ahead and build this.. using /feature-dev:feature-dev

Phase 9 · 20-09-2026, mid-morning

Three reviewers, in parallel, before calling it done

Rather than one reviewer, this round used three independent code-reviewer subagents dispatched in parallel, each briefed on a different lens: simplicity and duplication, correctness and bugs, and adherence to this project's own conventions and the approved spec.

ReviewerWhat it found
Simplicity / DRYThe new web API route duplicated ~85% of the existing plan route, including the trickiest part (SSE disconnect handling) — the extraction done on one side of the codebase was never mirrored on the other.
Correctness / bugsThree real logic gaps: extending a non-last city in the itinerary had contradictory date math; a city name was never checked against the itinerary's actual cities before being trusted; and a multi-visit itinerary (same city twice) could leave a stale, unreachable inter-city leg after a cutoff. Also: the new agent was never registered in the web UI's event-attribution list, so its work would have silently shown up as generic orchestrator activity.
Conventions / spec fidelityA semicolon slipped into the new agent's own prompt file — violating a rule that file itself states, a repeat of an exact defect class fixed once before. Also: the spec's new subsections were numbered wrong, colliding with an existing section.
Aman, after the consolidated findings 20-09-2026 10:02
fix all 8
What happened
All eight were fixed in one pass, re-verified with the full test suite, and one reviewer suggestion was deliberately rejected rather than blindly applied: a suggested permission-flag change would have quietly broken the eval script's ability to write files, because this exact project had already discovered (and documented, as D-022) a real quirk in how Claude Code's permission system checks path-scoped rules. Applying every review comment without cross-checking prior decisions would have reintroduced a bug that had already been fixed once.

A follow-up closed a real coverage gap in the new tests — three more fixtures (a round-trip city, a non-terminal city extension, an unknown city) were added specifically because the first three fixtures never exercised the bugs the review round had just found:

Aman 20-09-2026 10:08
lets go ahread as per recommendation and fix those
Pattern worth stealing
Multiple reviewers with different lenses, dispatched in parallel, found different classes of problem that a single reviewer likely would have missed one of. And a review finding is a recommendation, not an order — it should be checked against what the project already knows, not applied on faith.

Phase 10 · 20-09-2026, late morning

Using the new feature for real, immediately

The very next thing Aman did with the finished trip-revision feature was use it on his own real, already-planned France trip — not a test fixture.

Aman 20-09-2026 10:24
Yeah, sure. I'm on a 3-day trip from Ahmedabad to France, and I would like to extend it to 2 more days. Adjust my travel plan and let me know what could be the places that I can visit in the next 2 days.

This single request surfaced things no amount of fixture testing had: the existing France trip had no real dates on file at all (it predated the date-backfill work), the classifier correctly refused to guess them, and once real dates were supplied, the request named Marseille — a city that was never part of the original trip. The classifier, exactly as designed, refused to invent a new city stop.

A real scope gap, found by dogfooding, not by review
The original design had explicitly deferred "adding a new city to an existing trip" as out of scope. Faced with an actual user wanting exactly that, the right call was to widen the scope on the spot: if the city is explicitly named by the user, trust it and append it at the end of the trip with full re-verification, rather than reflexively refusing. Logged as a scope amendment (D-036) to the same spec section, with the reasoning: refusing an explicit instruction is a worse failure than the caution the deferral was meant to prevent.
A fabricated number, caught before it shipped
While verifying walking times for the new Marseille day, the routing tool returned "17 minutes" between two stops. That number implied roughly 16.6 km/h on foot — physically impossible, and Château d'If is in fact an island fort reachable only by ferry. Rather than report it, the number was rejected and the leg was honestly marked "could not verify," with a note that a ferry crossing needs to be booked separately. The final itinerary also carried an honest warning that the worst-case budget (if every unverified fare landed at the top of its estimated band) would exceed the $3,000 limit by $164 — not hidden, shown plainly with the mitigation already on file.
Pattern worth stealing
Every fix in this entire project that mattered was found by looking at a real output, not by reasoning about the code in the abstract — a screenshot of a broken table, a real French trip exposing a Japan-only assumption, and finally the new revision feature immediately meeting a request its own designer hadn't scoped for. A system is only as good as its last real use, and the discipline throughout was to treat that as information, write it down, and fix the actual cause.

Summary

Patterns worth stealing for your own project

  1. Brainstorm before you build, with a hard gate. No spec, no code, until the human has approved a design in chat. A one-line redirect asked early ("are there real APIs?") is nearly free; asked after Task 9 it is a rewrite.
  2. Three files, three jobs, never merged. A decision log (why we chose X over Y), a spec changelog (where the shipped code drifted from the approved design and why), and a feedback log (every correction, generalized into a reusable check). A future session with zero memory of the conversation can pick up exactly where it left off by reading these.
  3. An independent reviewer sees the artifact, never the reasoning. The reviewer that caught the Python pin, the commit trailer, and the "test doesn't prove what it claims" bugs never saw the implementer's intent — only the diff and the brief. That's what let it ask "what would make this pass even if the property were false?" instead of trusting the story.
  4. A review finding is a recommendation, not an order. One suggested fix was correctly rejected because it contradicted something this project had already verified and documented. Blind compliance with every review comment would have reintroduced a fixed bug.
  5. Multiple reviewers with different lenses beat one generalist reviewer. Simplicity, correctness, and convention-fidelity each found things the others missed, dispatched in parallel rather than sequentially.
  6. A green test suite proves the assertions passed, not that the guarantee holds. The recurring "does this test actually prove what it claims" catch appeared at least three separate times across this project, on different code.
  7. Nothing beats using the real thing. Every substantive fix in this project traced back to a real screenshot, a real second destination, or a real personal trip — never to abstract code review alone.
  8. Root-cause, don't patch the visible symptom. A broken table in one file turned out to be a missing template rule shared by four agent files. A "Japan-only" bug turned out to be a missing fallback path that had simply never been written for anywhere else.
  9. When you widen scope mid-build, say so, in the same place the original scope was written. The Marseille extension wasn't just coded — the spec section that had explicitly deferred it was amended, with the reasoning for the change on record next to the original decision.
